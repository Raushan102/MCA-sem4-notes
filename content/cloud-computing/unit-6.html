CLOUD COMPUTING

Unit VI: Cloud and SOA

THE CENTRAL IDEA

Service-Oriented Architecture (SOA) is a way to design software as a collection of independent, reusable services. Cloud computing supplies computing resources—such as servers, storage and networks—over a network. SOA describes how software capabilities are organised and used; cloud describes how computing resources and services are delivered. They can work together, but they are not the same thing.

1. SOA Journey To Infrastructure

YELLOW Exam focus: this topic appears in the supplied compiled question collection, not as a confirmed direct question in the primary paper.

1.1 What does “journey to infrastructure” mean?

SOA first became popular as an approach for organising business software functions into reusable services. Over time, organisations realised that these services also depend on common technical resources: computing power, storage, networks, identity, security, monitoring and deployment tools. The SOA journey to infrastructure describes the move from making only application functions reusable to treating the underlying IT capabilities as services too.

In simple terms: earlier, a company might build a separate server, storage setup and network configuration for every application. A service-oriented approach encourages common capabilities to be provided once and reused by many applications or teams.

1.2 The stages of this journey

  1. Application silos: each department builds and operates its own application and supporting systems. Similar functions are duplicated.
  2. Application integration: systems are connected so that they can exchange information. Interfaces and common communication rules reduce manual data transfer.
  3. Business services: common business functions—such as customer lookup, billing, order processing or payment validation—are exposed as reusable services.
  4. Shared IT services: technical capabilities such as identity management, logging, messaging, database access and monitoring are offered for reuse.
  5. Service-oriented infrastructure: compute, storage, network, security and deployment capabilities are pooled, automated and made available when required.
  6. Cloud-style delivery: infrastructure resources can be requested on demand, provisioned rapidly, measured and released when no longer needed.

Important: this is a conceptual progression for understanding the syllabus phrase. It is not a mandatory six-step industry standard that every organisation must follow in exactly this order.

1.3 Diagram — from application silos to service-oriented infrastructure

1.4 Example

Imagine a college portal. The student registration system, library system and examination system all need to identify a student. Instead of each application maintaining a different student identity function, the college can expose a common student-information service. The systems reuse it. The servers, storage, network and monitoring that run these services can then be provided through shared IT infrastructure.

1.5 Why move towards infrastructure services?

  • Reduce duplicated hardware and software resources.
  • Make common capabilities available to multiple applications.
  • Provision resources faster through automation.
  • Improve consistency of security, monitoring and maintenance.
  • Scale shared resources as demand changes.
  • Support cloud delivery and more efficient resource utilisation.

2. SOA And Cloud

RED High priority: the supplied primary MCA Semester IV paper includes “Explain SOA and its relationship with Cloud Computing.” The compiled question collection also includes this topic.

2.1 First understand the two terms separately

SOA (Service-Oriented Architecture) is a software architecture approach in which application capabilities are organised as services. A service exposes a defined interface so that other applications or services can use it without needing to know its internal implementation.

Cloud computing is a model for providing shared computing resources—such as servers, storage, networks, platforms and applications—over a network, often with on-demand provisioning and measured usage.

2.2 How are SOA and cloud related?

SOA and cloud complement each other. SOA helps organise what capabilities software offers and how systems interact. Cloud provides where and how the computing resources are delivered to run those services. An organisation can build SOA services and host them in its own data centre, in a public cloud, in a private cloud or across a hybrid environment.

2.3 Similarities

  • Service-based thinking: both emphasise delivering capabilities as services.
  • Abstraction: users work through interfaces instead of dealing with every internal detail.
  • Reuse and sharing: services or resources can support multiple consumers.
  • Network access: services are commonly accessed over networks.
  • Scalability: both can support systems that grow as demand increases, although the mechanisms differ.

2.4 Differences between SOA and cloud computing

BasisSOACloud computing
Main focusHow software capabilities are designed and connected.How computing resources and services are delivered.
Primary concernService interfaces, reuse, interoperability and composition.Provisioning, resource pooling, elasticity, access and measurement.
What it organisesBusiness and application functions.Compute, storage, network, platforms and hosted applications.
Where it runsOn-premises, cloud or hybrid environments.Provider or organisation-managed cloud infrastructure.
RelationshipCan be used without cloud.Can host applications that are not designed using SOA.

2.5 Example

An online shopping application may use separate services for customer accounts, product catalogue, payment and order tracking. That is the SOA-style organisation of software capabilities. If these services run on virtual machines, storage and networks rented from a cloud provider, the deployment uses cloud computing too.

Do not write this incorrect statement: “SOA and cloud computing are the same.” The correct idea is: SOA is an architectural approach; cloud is a service-delivery and resource-provisioning model. Cloud can support SOA, and SOA-based applications can run outside the cloud.

2.6 Benefits of combining SOA and cloud

  1. Reusable services can be deployed on flexible cloud resources.
  2. Cloud infrastructure can scale to meet changing service demand.
  3. On-demand provisioning can reduce the time needed to create environments.
  4. Shared services and pooled infrastructure can improve utilisation.
  5. Cloud monitoring and metering can help track resource consumption and cost.

3. SOA Defined

RED High priority: “Define SOA in Cloud Computing” appears in the supplied question collection and primary-paper context. Prepare the definition and diagram carefully.

3.1 Definition

Service-Oriented Architecture (SOA) is an architectural approach in which software functionality is organised into independent, reusable and interoperable services. Each service exposes a well-defined interface or contract. Other applications can discover or call the service without needing to know how its internal code works.

In easy words, instead of building one huge application where every function is tightly connected, we divide the application into useful services. Each service performs a particular task and communicates with other services through agreed interfaces.

3.2 What is a service?

A service is a self-contained software capability that performs a defined task for a consumer. Examples include checking a customer's details, calculating tax, processing a payment or tracking an order. A service hides its internal implementation and exposes only the information needed to use it.

3.3 Main components / participants of SOA

  • Service provider: creates, hosts or maintains a service and makes it available to others.
  • Service consumer: the application, system or another service that requests and uses a service.
  • Service registry: a directory where service descriptions can be published and discovered. A registry is useful in registry-based discovery; not every modern SOA deployment must use a separate registry.
  • Service contract / description: defines what the service does, its interface, message format, policies and rules for interaction.
  • Service interface: the defined way in which a consumer communicates with the service.

3.4 SOA interaction — publish, find and bind

  1. Publish: the provider publishes a description of the service in a registry or another discovery mechanism.
  2. Find: the consumer searches for a service that meets its need.
  3. Bind / invoke: the consumer uses the service interface and contract to send a request and receive a response.

3.5 Important principles of SOA

PrincipleSimple meaningExample
Loose couplingServices depend as little as practical on the internal details of other services.Payment service uses a published interface, not another service's private code.
ReusabilityA service can be used by more than one application.One customer-verification service used by sales and support portals.
AbstractionInternal implementation is hidden behind the interface.Consumer requests a payment without knowing the bank integration code.
AutonomyA service controls its own logic and resources within its boundaries.Order service manages its own order-processing rules.
Standardised contractServices communicate through clearly described interfaces and rules.Documented request and response format.
DiscoverabilityServices have descriptions that help consumers find and understand them.Searching a service catalogue.
ComposabilitySeveral services can be combined to complete a larger task.Checkout combines inventory, payment and delivery services.

3.6 Advantages and limitations

Advantages: reuse of functions, easier integration, improved interoperability, clearer separation of responsibilities, independent service updates and the ability to combine services into larger workflows.

Limitations: network communication adds latency; service contracts and versions need management; distributed failures are harder to debug; security must be enforced across service boundaries; and too many small services can increase operational complexity.

3.7 SOA is not the same as microservices

Microservices are a more specific architectural style that usually favours smaller independently deployable services and decentralised data/operations. SOA is a broader approach and can include services that are larger, shared or integrated through enterprise-level infrastructure. They are related, but the terms should not be treated as exact synonyms.

4. SOA and IaaS

YELLOW Exam focus: “Explain SOA and IaaS in detail” and “Explain the relationship between SOA and IaaS” appear in the supplied compiled question collection.

4.1 What is IaaS?

Infrastructure as a Service (IaaS) is a cloud service model in which a provider offers fundamental computing resources—such as processing, storage and networking—so that a customer can deploy and run operating systems and applications. The customer usually manages the guest operating system, deployed applications and much of the configuration, while the provider manages the underlying physical cloud infrastructure.

Examples include renting a virtual machine, attaching cloud block storage and configuring a virtual network rather than buying and maintaining a physical server.

4.2 How does SOA relate to IaaS?

SOA structures the software into services. IaaS supplies the infrastructure on which those services can run. A service-oriented application can use IaaS virtual machines, storage and networks to host its service components. The infrastructure can be provisioned when needed and expanded as service demand grows.

4.3 Responsibilities in IaaS

Usually managed by cloud providerUsually managed by customer
Physical data centre and facilitiesGuest operating system configuration and updates
Physical servers and storage hardwareApplications and SOA services deployed on VMs
Physical networking and virtualisation platformData, identities, access policies and application-level security
Core cloud infrastructure availabilityWorkload configuration, service integration and backups according to chosen design

Exact responsibility boundaries vary by provider and service. The table shows the general IaaS model.

4.4 Benefits of using IaaS for SOA

  1. Flexible capacity: allocate more or fewer virtual machines as service demand changes.
  2. Faster provisioning: create development, testing and production environments without purchasing hardware.
  3. Resource pooling: multiple services can use shared infrastructure while remaining logically separated.
  4. Cost model: pay for provisioned or consumed resources according to the provider's pricing model.
  5. Geographic reach: deploy services in different regions when required by latency, resilience or compliance needs.
  6. Automation: infrastructure can be created and configured through APIs and templates.

4.5 Example

A company runs four SOA services: customer, product, order and payment. It rents three cloud virtual machines, configures a virtual network and attaches storage using IaaS. The services are deployed on those machines and communicate through their interfaces. When orders increase, the company can add compute capacity or more service instances, subject to its architecture and cloud configuration.

Remember the distinction: IaaS does not automatically create SOA. IaaS provides infrastructure. The application team must still design, build, integrate and operate its services.

5. SOA-Based Cloud Infrastructure Steps

BLACK No direct or related question was identified for this exact topic in the supplied question collection. It remains part of the official syllabus and must be studied.

5.1 Meaning

An SOA-based cloud infrastructure is a cloud environment designed to host and support applications that are organised as services. It combines service-oriented application design with cloud infrastructure capabilities such as virtual machines, storage, networking, security, monitoring and automated provisioning.

5.2 Steps to build / establish it

  1. Identify business requirements: understand what the organisation needs, who will use the system, expected workload, availability, security and compliance requirements.
  2. Identify and define services: divide application functionality into clear business or technical services. Define each service's purpose, inputs, outputs and owner.
  3. Define service contracts and interfaces: document how services communicate, including message formats, API operations, authentication and error handling.
  4. Choose the cloud deployment and service model: select public, private or hybrid cloud, and decide whether IaaS, PaaS or a combination best fits the workload.
  5. Design the infrastructure: plan compute, storage, network, identity, security boundaries, backup, availability and disaster recovery.
  6. Provision resources: create virtual machines or other compute resources, networks, storage and required platform components. Use automation or infrastructure templates where practical.
  7. Deploy and integrate services: deploy each service, configure service-to-service communication, connect data sources and test the end-to-end business workflow.
  8. Apply security and governance: configure identity and access management, encryption, secrets handling, network controls, audit logs, policies and service ownership.
  9. Monitor and measure: monitor availability, latency, errors, resource usage, security events and cost. Define service-level objectives where appropriate.
  10. Scale, maintain and improve: scale resources as demand changes, patch components, update service versions, test recovery and improve based on monitoring data.

5.3 Diagram — SOA-based cloud infrastructure workflow

5.4 Example

A university wants a cloud-based student portal. It first identifies functions such as login, student records, fee payment and examination results. It defines these as services with documented interfaces. It then chooses a cloud model, provisions compute, database/storage and network resources, deploys the services, secures access, tests service communication and monitors performance. During admission season, it scales capacity to handle higher traffic.

5.5 Common mistakes to avoid

  • Starting with virtual machines before understanding business requirements.
  • Creating services without clear interfaces or ownership.
  • Assuming cloud hosting automatically makes an application service-oriented.
  • Ignoring identity, network security, data protection and backups.
  • Monitoring only CPU and memory while ignoring service errors and response time.

6. SOA Business And IT Services

BLACK No direct or related question was identified for this exact topic in the supplied question collection. Study the distinction and examples because it is explicitly in the official syllabus.

6.1 Business services

Business services represent activities or capabilities that directly support an organisation's business processes and goals. They express what the organisation does, not the technical details of how its computers work.

Examples: customer registration, order processing, payment approval, inventory checking, student admission, fee collection and result publication.

6.2 IT services

IT services provide the technical capabilities and infrastructure that applications and business services need to operate. They support the delivery, security, integration and management of IT systems.

Examples: identity and access management, database hosting, storage, network connectivity, backup, monitoring, logging, messaging, virtual machine provisioning and application deployment.

6.3 Business services vs IT services

BasisBusiness servicesIT services
PurposeDeliver a business capability or outcome.Provide technology support needed to run systems.
FocusBusiness process and user requirement.Technology, infrastructure and operations.
UsersCustomers, students, employees or business applications.Applications, developers, administrators and business services.
ExamplesOrder placement, fee payment, customer onboarding.Authentication, database, storage, backup, network.
Success measured byProcess completion, customer experience, accuracy and business value.Availability, performance, security, recovery and support quality.

6.4 How they work together

Business services often depend on IT services. For example, a fee payment business service may depend on an identity service to confirm the student, a database service to retrieve fee details, a payment gateway integration to collect money, a messaging service to send confirmation and a logging service to keep an audit record.

6.5 Categories of IT services in an SOA environment

  • Infrastructure services: compute, virtual machines, storage and networking.
  • Platform services: runtime environments, databases, middleware and messaging.
  • Security services: authentication, authorisation, encryption and key management.
  • Integration services: API gateways, message brokers and service communication.
  • Operations services: monitoring, logging, backup, incident handling and deployment automation.

6.6 Why separate business and IT services?

  • Business logic can change without redesigning every infrastructure component.
  • Common IT capabilities can be reused by many business services.
  • Responsibilities become clearer: business owners focus on outcomes; IT teams operate technical capabilities.
  • It becomes easier to measure business performance and technical service quality separately.
  • Changes can be planned and managed at the correct layer.

7.2 One-mark definitions

  1. SOA: an architectural approach that organises software capabilities as reusable, interoperable services with defined interfaces.
  2. Service: a capability offered through a defined interface for a consumer to use.
  3. Service provider: the person or organisation that offers a service.
  4. Service consumer: the application or entity that requests and uses a service.
  5. Service registry: a directory of service descriptions that supports service discovery.
  6. IaaS: a cloud model that provides processing, storage and networking resources to deploy software.
  7. Loose coupling: designing services to minimise dependency on the internal details of other services.
  8. Service reusability: designing a service so that multiple consumers or applications can use it.

7.3 Common confusions

  • SOA vs cloud: software architecture vs resource/service delivery model.
  • SOA vs microservices: broad architectural approach vs a more specific style of small independently deployable services.
  • Service vs API: a service is the capability; an API/interface is one way to access it.
  • Provider vs consumer: provider offers the capability; consumer uses it.
  • Registry vs service: registry helps locate a service; it does not normally perform the business function itself.
  • IaaS vs SOA: IaaS supplies infrastructure; SOA organises application capabilities.
  • Business service vs IT service: business service delivers a business outcome; IT service supplies technical support.
