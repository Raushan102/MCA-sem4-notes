Unit VII — Cloud Infrastructure Benchmarking

THE CENTRAL IDEA

Benchmarking means testing a system with a defined workload and measuring the results. It helps us answer: How much work can this cloud infrastructure handle? How quickly does it respond? Does performance remain stable when users increase? And what resources or cost are required?

KEY TERMS BEFORE STARTING

Workload: the tasks given to a system during a test. Metric: a number used to describe performance. Throughput: completed work per unit of time. Latency/response time: time taken for an operation or request. Scalability: ability to handle increased workload by adding resources. Repeatability: ability to obtain comparable results when the same test conditions are repeated.

1. OLTP Benchmark

RED

1.1 What is OLTP?

OLTP stands for Online Transaction Processing. It is a type of computer system designed to process a large number of short, routine transactions quickly and reliably. Each transaction usually reads or changes a small amount of data.

Think of a bank ATM. When a customer withdraws ₹1,000, the system checks the account, verifies the balance, deducts the amount and records the transaction. Many customers may perform such operations at the same time. This is an OLTP workload.

1.2 Main characteristics of OLTP

  • Many concurrent users: many users perform transactions at the same time.
  • Short transactions: each transaction normally completes quickly.
  • Frequent read and write: data is inserted, updated, deleted and retrieved.
  • Correctness: transactions must preserve database consistency.
  • Low response time: users expect a quick answer.
  • High transaction rate: the system should complete many transactions per second or minute.

1.3 What is an OLTP benchmark?

An OLTP benchmark is a standardised test that runs a transaction-oriented workload against a database or complete system and measures how well it handles that workload. It helps compare database servers, CPUs, memory, storage and cloud infrastructure under similar conditions.

A well-known example is TPC-C, published by the Transaction Processing Performance Council (TPC). It models an order-entry business. Its five transaction types include New-Order, Payment, Order-Status, Delivery and Stock-Level. The principal throughput metric is tpmC — New-Order transactions per minute, while the other required transaction types are also running.

1.4 OLTP benchmark metrics

MetricMeaning
Transactions per second (TPS)Number of completed transactions each second.
tpmCTPC-C New-Order transactions per minute under its defined transaction mix.
Response timeTime taken for a transaction to complete from the user's perspective.
AvailabilityWhether the service remains accessible when required.
Price/performanceCost considered alongside the achieved benchmark performance.

1.5 OLTP vs OLAP benchmark — important difference

OLAP means Online Analytical Processing. OLTP handles daily business transactions; OLAP analyses large amounts of stored data to support decisions. OLAP workloads often execute complex queries, scans and aggregations over large datasets.

BasisOLTP benchmarkOLAP / BI benchmark
Main purposeMeasure transaction processing.Measure analytical and decision-support processing.
WorkloadMany short read/write transactions.Complex queries, joins, aggregation and reporting.
Data accessUsually small records or selected rows.Often scans large volumes of data.
UsersMany concurrent transaction users.Analysts, reporting users and query workloads.
Important metricsTPS, tpmC, response time and transaction correctness.Query response time, query throughput and data-maintenance performance.
ExampleTPC-C.TPC-DS and TPC-H.
Typical useBanking, booking, order entry and payments.Business reports, trends, forecasting and decision support.

EXAM MEMORY TIP

OLTP = run the business. OLAP = analyse the business. OLTP benchmark = transaction speed and correctness. BI/OLAP benchmark = analytical query and data-processing performance.

1.6 Advantages and limitations

Advantages: gives measurable evidence, helps compare configurations, exposes bottlenecks, supports capacity planning and can reveal price/performance trade-offs.

Limitations: a benchmark is only a model of real work. A high score does not guarantee that every real application will be fast. Results can be misleading if data size, software tuning, cloud region, instance type or workload are different.

2. Business Intelligence Benchmark

YELLOW

2.1 What is Business Intelligence (BI)?

Business Intelligence means collecting, organising and analysing business data so that managers and employees can make better decisions. BI systems answer questions such as: Which product sold the most? Which region's sales are falling? How did revenue change this quarter?

BI commonly uses a data warehouse or analytical data platform. Data may come from sales systems, websites, finance applications and customer databases. It is cleaned and combined before analysts run reports and queries.

2.2 What is a Business Intelligence benchmark?

A BI benchmark is a controlled test used to measure how efficiently a system performs analytical work. It may test large data scans, complex SQL queries, joins, aggregations, reporting, data refresh and concurrent analytical users.

A major example is TPC-DS. It models a decision-support environment for a retail business. It evaluates a range of queries and data-maintenance operations. TPC-DS reports query response time in single-user mode, query throughput in multi-user mode and data-maintenance performance.

2.3 What does a BI benchmark measure?

  • Query response time: how long an analytical query takes.
  • Query throughput: how many queries can be completed over a period under a defined multi-user test.
  • Data maintenance: how efficiently data can be loaded, refreshed or updated.
  • Scalability: how performance changes as data volume and users increase.
  • Resource use: CPU, memory, storage I/O and network use during the test.

2.4 Example

Suppose a retail company stores five years of sales data. A BI benchmark can run queries that calculate monthly revenue, compare product categories and identify regional trends. The test records how long the queries take and how the system behaves when several analysts run reports together.

2.5 BI benchmark vs OLTP benchmark

BI tests are generally read-heavy and analytical, while OLTP tests focus on short operational transactions that frequently modify records. BI benchmarks help evaluate data warehouses, analytical databases and big-data platforms.

3. E-Business Benchmark

BLACK

3.1 Meaning of E-Business

E-Business means conducting business activities through electronic networks, especially the internet. Examples include online shopping, ticket booking, digital banking, online payment and customer portals.

An e-business application typically includes a web server, application server, database, network and sometimes payment or identity services. When many customers visit at once, the complete application must respond reliably.

3.2 What is an E-Business benchmark?

An E-Business benchmark is a performance test that simulates realistic online business activity and measures how well the web or application infrastructure serves users. The workload may include browsing product pages, searching, adding items to a cart, logging in, checking out and submitting orders.

Unlike a test that measures only raw CPU speed, an end-to-end e-business benchmark considers the application stack and the interactions between web, application, database and network components.

3.3 Important measurements

MeasurementWhat it tells us
Requests per secondHow many HTTP requests the system serves each second.
Transactions per secondHow many complete business actions are completed each second.
Response time / latencyHow long a user waits for a response.
Error ratePercentage or count of failed requests.
Concurrent usersHow many simulated users are active at the same time.
AvailabilityWhether the service is accessible during the test.

3.4 Example

An online shopping website expects 5,000 visitors during a sale. A benchmark tool simulates users searching products, opening product pages and placing orders. If response time rises sharply or checkout requests fail, the test reveals a capacity or application bottleneck before the real sale.

3.5 Benefits

  • Tests whether an online business can handle peak traffic.
  • Finds bottlenecks across web, application, database and network layers.
  • Helps estimate infrastructure capacity before a launch or sale.
  • Allows comparison of server or cloud configurations using the same workload.

4. ISV Benchmarks

BLACK

4.1 What is an ISV?

ISV stands for Independent Software Vendor. An ISV is a company that develops and sells software products independently of the hardware or cloud platform on which the software runs. Examples of software categories include ERP, CRM, database, accounting, analytics and enterprise applications.

4.2 Meaning of ISV benchmark

An ISV benchmark is a performance evaluation that uses an application or workload associated with a software vendor to assess how well a system runs that software. It may test an ERP application, database, CRM platform or other business software on a particular server or cloud configuration.

The goal is to understand application-level performance, not just the speed of an isolated hardware component. The benchmark should represent realistic application operations and should record the software version and system configuration.

4.3 How it works

  1. Select the business application and a representative workload.
  2. Prepare the test environment, including cloud instance, operating system, database and application version.
  3. Load representative data and configure the application.
  4. Run the same defined workload under controlled conditions.
  5. Measure response time, throughput, resource use, errors and, where relevant, cost.
  6. Publish the setup and results so another person can understand and reproduce the test.

4.4 Why are ISV benchmarks useful?

  • Show whether a business application performs well on a proposed infrastructure.
  • Help customers size cloud resources before deployment.
  • Support comparison of hardware, virtual machines and cloud configurations.
  • Reveal application-specific bottlenecks that generic CPU tests may miss.
  • Help vendors and customers validate performance expectations.

4.5 Important caution

A result for one application and version does not automatically predict the performance of another application. Even the same application may behave differently with different data sizes, user counts, configuration settings and software versions. Always read the benchmark conditions.

5. Cloud Performance Data Collection

YELLOW

5.1 Meaning

Cloud performance data collection is the process of gathering measurements from cloud resources and applications so that their performance, health, capacity and bottlenecks can be understood.

Cloud systems are distributed. An application may run across virtual machines, containers, databases, storage services and networks. Collecting data from these components gives a more complete picture than checking only one server.

5.2 Main categories of performance data

CategoryExamplesWhat it helps identify
CPUCPU utilisation, load, CPU timeWhether processors are busy or saturated.
MemoryUsed/available memory, cache, swap, page faultsMemory pressure or swapping.
Storage / diskIOPS, read/write throughput, latency, queue depth, capacitySlow disks, storage saturation or lack of space.
NetworkBandwidth, bytes in/out, packet loss, errors, latencyNetwork congestion or connectivity issues.
ApplicationRequest rate, response time, error rate, active sessionsSlow APIs, failing requests or application bottlenecks.
DatabaseQuery duration, connections, locks, cache hit ratioSlow queries, contention or connection exhaustion.
Cloud platformInstance health, provisioning time, scaling eventsInfrastructure health and elasticity behaviour.

5.3 Important performance terms

  • Utilisation: percentage of a resource currently being used.
  • Throughput: amount of work completed per unit of time, such as requests/second or MB/second.
  • Latency: time taken for one operation or request.
  • IOPS: input/output operations per second, commonly used for storage.
  • Error rate: number or percentage of operations that fail.
  • Availability: proportion of time a service is accessible.
  • Queue depth: number of operations waiting to be processed.

5.4 Data collection process

  1. Choose objectives: decide what question the measurement should answer, such as whether the database is slow.
  2. Select metrics: choose CPU, memory, disk, network and application metrics relevant to that question.
  3. Collect data: use cloud monitoring agents, platform APIs, application instrumentation and logs.
  4. Store and organise: keep timestamps, resource identifiers, regions, instance types and software versions with the measurements.
  5. Visualise and analyse: use dashboards, reports and comparisons to identify trends and bottlenecks.
  6. Alert and improve: define thresholds or anomaly alerts, investigate the cause and adjust resources or application design.

5.5 Metrics, logs and traces — do not confuse them

Data typeMeaningExample
MetricsNumerical measurements collected over time.CPU = 78%, API latency = 240 ms.
LogsTime-stamped records of events.“Payment request failed: timeout”.
TracesShow the path of one request across multiple services.Request spends 20 ms in gateway and 500 ms in database.

5.6 Example using a cloud application

Suppose a web application becomes slow at peak time. CPU metrics show 35% utilisation, but database query latency increases and disk I/O wait is high. This suggests the problem may be storage or database-related rather than a lack of CPU. By collecting multiple metric categories together, the administrator can investigate the correct component instead of blindly increasing virtual machine size.

5.7 Good practices

  • Collect data before, during and after a benchmark run.
  • Use consistent time intervals and synchronised clocks.
  • Record the cloud region, instance type, storage type, software versions and workload settings.
  • Keep raw results; do not publish only a final score.
  • Collect enough samples to understand variation, not just one lucky run.
  • Avoid collecting sensitive data unnecessarily; apply access control and retention rules.

6. Performance Monitoring Commands

BLACK

6.1 Why do we need commands?

Performance monitoring commands are utilities used by system administrators and developers to inspect a running machine. They help identify whether a system is limited by CPU, memory, disk, network or a particular process. In cloud virtual machines, these commands are useful because the guest operating system can reveal what is happening inside the instance.

6.2 Common Linux performance commands

CommandPurposeExample
topLive view of processes, CPU, memory and system load.top
htopInteractive process viewer (may need installation).htop
psSnapshot of running processes.ps aux
freeMemory and swap usage.free -h
vmstatProcesses, memory, paging, block I/O and CPU statistics.vmstat 1 5
iostatCPU and disk I/O statistics, including extended device metrics.iostat -xz 1
dfFilesystem space usage.df -h
duSpace used by a directory or file tree.du -sh /var/log
sarCollects and reports historical system activity (sysstat package).sar -u 1 5
uptimeSystem running time and load averages.uptime
ssSocket and network connection information.ss -tuln
ip -s linkNetwork interface statistics, including errors and dropped packets.ip -s link
pingChecks reachability and round-trip time to a host.ping -c 4 example.com

6.3 Important commands explained

1. top — displays a live summary of system load and running processes. It helps identify which process is using CPU or memory.

top
# Press P to sort by CPU usage
# Press M to sort by memory usage
# Press q to quit

2. free -h — shows memory and swap values in human-readable units. Pay attention to the available memory value rather than assuming that all memory shown as used is unavailable.

free -h

3. vmstat 1 5 — prints system statistics every one second, five times. It includes process, memory, swap, block I/O and CPU information. The first report can represent averages since boot; subsequent reports represent the sampling interval.

vmstat 1 5

4. iostat -xz 1 — shows extended CPU and disk I/O statistics every second. Useful columns include read/write operations per second, throughput, average queue size and await (average I/O time).

iostat -xz 1

5. df -h — checks whether a filesystem is running out of space.

df -h

6. ss -tuln — displays listening TCP/UDP sockets and ports. Useful when investigating network services and port availability.

ss -tuln

7. sar -u 1 5 — reports CPU utilisation samples. The sysstat package must be installed and data collection configured for historical reports.

sar -u 1 5

6.4 A simple troubleshooting sequence

  1. Run uptime to check load averages.
  2. Run top to find processes consuming CPU or memory.
  3. Run free -h and vmstat 1 to inspect memory pressure and swapping.
  4. Run iostat -xz 1 to check disk I/O and latency.
  5. Run ss -s or ip -s link to inspect network activity.
  6. Check application and system logs for errors and timeouts.

IMPORTANT: A single high value does not always prove a bottleneck. Observe repeated samples and relate them to application response time and workload. For example, high disk latency together with a growing I/O queue is stronger evidence than one isolated reading.

7. Benchmark Tools

BLACK

7.1 Meaning

Benchmark tools are software utilities or benchmark suites used to generate a defined workload, measure system behaviour and report performance results. Different tools test different layers. A CPU benchmark cannot by itself tell us whether a database or website will perform well.

7.2 Common benchmark tools and suites

Tool / suiteAreaWhat it is used for
TPC-COLTP databaseStandard transaction-processing workload; reports tpmC and related metrics.
TPC-DS / TPC-HBI / decision supportAnalytical queries, data processing and decision-support performance.
SPEC Cloud IaaSCloud infrastructureEvaluates IaaS cloud performance and scalability under a defined test suite. Check benchmark version and status before using results.
SPECwebWeb serverMeasures web-serving performance under standardised workloads.
SPEC CPUCPU / computeMeasures compute-intensive processor and system performance.
sysbenchCPU, memory, database, threadsRuns configurable tests for quick system and database comparisons.
UnixBenchGeneral Unix/Linux systemProvides a set of system performance tests; results depend on configuration.
fioStorage I/OGenerates configurable read/write workloads and measures IOPS, throughput and latency.
iperf3NetworkMeasures network throughput between two endpoints.
Apache JMeterApplication / web loadGenerates load for web applications and APIs; measures response times and errors.
wrkHTTP loadGenerates HTTP requests to test web-server throughput and latency.

7.3 How to choose the right tool

  • Need to test database transactions? Choose a database workload such as TPC-C or a suitable database test tool.
  • Need to test analytics? Choose TPC-DS or TPC-H style analytical workloads.
  • Need to test CPU? Use SPEC CPU or a suitable CPU test.
  • Need to test storage? Use fio with a workload matching expected reads and writes.
  • Need to test network bandwidth? Use iperf3 between endpoints.
  • Need to test a website or API under user load? Use JMeter, wrk or an equivalent load generator.
  • Need to evaluate an IaaS platform? Use a cloud benchmark suite such as SPEC Cloud IaaS, subject to its current availability and rules.

7.4 Steps for a fair benchmark

  1. Define the purpose and choose a representative workload.
  2. Use equivalent hardware, software versions, data size and configuration when comparing systems.
  3. Record cloud region, instance type, storage type, network settings and prices where relevant.
  4. Warm up the system if the benchmark methodology requires it.
  5. Run the test multiple times and retain raw output.
  6. Measure throughput, latency, errors and resource utilisation.
  7. Report the methodology and limitations, not just the highest score.

7.5 Benchmarking mistakes to avoid

  • Comparing different workload sizes as if they were equal.
  • Changing several configuration variables at once.
  • Reporting only peak throughput while hiding poor response times or errors.
  • Ignoring cost, region, storage and network differences in cloud comparisons.
  • Using a synthetic test that does not represent the real application.
  • Failing to repeat tests or disclose the environment.
